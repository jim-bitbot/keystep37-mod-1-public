## USB descriptor summary

Full dump: `firmware-re/descriptors/lsusb_verbose_dump.txt`

- VID:PID `1c75:0219` (Arturia KeyStep 37), full-speed USB 2.0
- Two interfaces, both USB Audio class (0x01):
  - Interface 0: AudioControl (0x01/0x01), no endpoints — just the class header
  - Interface 1: MIDIStreaming (0x01/0x03) — one bulk OUT (EP 0x02, 64B) and one
    bulk IN (EP 0x81, 64B), one embedded MIDI IN jack + one embedded MIDI OUT jack
- **No interface class 0xFE (Application Specific) and no DFU descriptor anywhere.**
  Confirms the device does not expose a USB-DFU interface — SWD remains the only
  flashing fallback; `dfu-util` has nothing to attach to over this USB link.
- **No HID interfaces.** Pads/knobs/buttons are not HID reports — they go out as
  regular MIDI (CC/note/vendor CC) over the MIDIStreaming interface, as already
  seen in the earlier capture (`captures/keystep_midi_test_20260920.txt`).

## Arturia MIDI Control Center device descriptor (KeyStep37.json)

Pulled directly from the live Windows install at
`C:\ProgramData\Arturia\MIDI Control Center\Resources\KeyStep37.json`
(copied here as `firmware-re/notes/KeyStep37.json`).
This is Arturia's own device metadata — not documentation, but ground truth
for identifiers used by their protocol.

`firmware-re/notes/KeyStep37Test.json` (from the same Resources folder) is a
**separate, distinct file** — not a duplicate. It's a factory QA/repair-mode
descriptor (`"testfile": 1`, `"availables_modes_hardcoded": "REPAIR, QA, PROD,
PCBA"`), roughly 1000 lines longer than the normal descriptor. Not yet
analyzed in depth, but worth real attention later — factory test modes
often expose lower-level hardware diagnostics/self-test hooks not reachable
in normal consumer mode, which could be very useful for this project
(e.g. a cleaner way to probe hardware state without going through the
full application-mode SysEx protocol).

Key facts:
- `usbVendorId: 7285` = `0x1C75` — matches.
- `alternatives[0].usbProductId: 537` = `0x0219` — matches the normal-mode PID.
- **`firmwareUpdater.updaterUsbProductId: 657` = `0x0291`** — the device
  re-enumerates under a *different* USB PID while in firmware-upgrade/bootloader
  mode. Worth watching for in `lsusb`/`dmesg` during an actual update, and
  relevant if we ever want to intercept/replicate the update handshake.
- `firmwareUpdater.name: "midiplus"`, `protocol: "arturia_v2"` — named protocol
  families, consistent with the "arturia_v2" tag also seen on other Arturia
  devices with SysEx-based control (per the existing MCC analysis doc).
- `extraParameters.productCode: 63`, `extraParameters.productKey: [90, 87, 110,
  40, 60, 78, 81]` — looks like a per-product key/seed used somewhere in the
  update or identification handshake. Tried it as a simple repeating-XOR key
  over the decoded firmware image; did not produce a recognizable vector table
  or code. **Open question** — could apply to a different stage (e.g. a
  challenge/response during the SysEx handshake, not the flashed image itself),
  or to specific header/checksum fields rather than the whole payload, or use a
  different XOR construction (e.g. per-block rather than per-byte-position).
  Worth revisiting once we've captured an actual firmware-update SysEx session.
- `deviceGlobalParametersId: 65` and the `fields[]`/`bulkOperation[]` sections
  give **paramId numbers for real device parameters** — e.g. paramId 96/97/98
  map to SEQ Length / SEQ Swing / SEQ Gate Length, paramId 101/102 to per-step
  Note Velocity / Note Pitch. These are very likely the same numeric IDs used
  inside the vendor SysEx protocol for get/set parameter messages — a strong
  lead for correlating captured SysEx bytes to specific settings once we do a
  SysEx capture during a MIDI Control Center session (not yet done).
- The `controls[]` section separately lists UI control IDs (different
  namespace from `paramId`) including `"chord"` as a first-class control and a
  `"seqarp"` control — both directly relevant to the project's Pattern-mode /
  chord-trigger objective in `README.md`.

## Firmware `.led` file — first-pass binary analysis

File: `og_firmware/keystep37_Firmware_Update_1_1_6_579 (1).led`
(234,280 bytes) — confirmed **hex-ASCII encoded text**, not raw binary
(matches what `README.md` already stated). Decoded to raw bytes:
`firmware-re/firmware-images/keystep37_1.1.6.579_decoded.bin` (117,140 bytes).

- `binwalk` on the raw hex-text file finds nothing (expected — it's text, not
  a binary container).
- `binwalk -Y` (capstone-based architecture scan) on the **decoded** binary
  found **valid ARM Thumb (16-bit) code starting at file offset `0x14` (20
  decimal), at least 2007 consecutive valid instructions.** This confirms
  Cortex-M/Thumb-2 target, consistent with the expected STM32 MCU.
- `strings` on the decoded binary shows heavy repetition of the byte pair
  `70 47` (renders as `"pG"` in ASCII) — this is Thumb opcode `0x4770`,
  **`BX LR`** (function return), one of the most common Cortex-M
  instructions. Strong independent confirmation of Thumb code, consistent
  with the binwalk finding.
- The first 20 bytes (`04 1C 68 74 DA 51 09 00 40 00 00 00 0A 00 00 00 04 00
  00 C0`) are **not** code — they parse as five little-endian 32-bit words:
  `0x74681C04`, `0x000951DA`, `0x00000040` (=64), `0x0000000A` (=10),
  `0xC0000004`. The two small plain-integer values (64, 10) look like real
  header fields (e.g. a length or count and a version), not code or a
  standard ARM vector table — this is almost certainly a small
  Arturia-specific container header prepended to the actual firmware image,
  exactly 20 bytes, before the real payload begins at `0x14`.
- The classic Cortex-M vector table (initial SP in the `0x20xxxxxx` RAM
  range, reset handler in the `0x08xxxxxx` flash range) was **not** found at
  either file offset `0x00` or `0x14` — the bytes there don't parse as valid
  addresses in either range. Likely explanation: what binwalk found at
  `0x14` is the start of a code region (possibly a bootloader-side loader
  stub or the app image with its own relocated/stripped vector table), not
  the interrupt vector table itself. Locating the real vector table (if
  present) and the actual entry point is the next real step, and belongs in
  Ghidra rather than ad hoc scripting — load
  `firmware-re/firmware-images/keystep37_1.1.6.579_decoded.bin` as raw binary,
  ARM little-endian, Cortex-M3/Thumb2, base address to be determined
  (try `0x08000000 + 0x14` as a starting guess for where analysis begins).

## Transport CC mapping — solved

The "vendor-specific" CCs seen in the very first capture (`captures/keystep_midi_test_20260920.txt`:
`B0 32`, `B0 33`, `B0 36`) are **not** unknown/vendor-specific at all. They're
the documented Transport-section CC assignments from `KeyStep37.json`:

| Physical button | Field (globalParamId) | Default CC | Observed |
|---|---|---|---|
| Rec | `Rec CC` (id 555, globalParamId 37) | 50 = `0x32` | `B0 32 7F` on press |
| Stop | `Stop CC` (id 554, globalParamId 36) | 51 = `0x33` | `B0 33 7F` on press |
| Play/Pause | `Play CC` (id 556, globalParamId 38) | 54 = `0x36` | `B0 36 7F` on press |

These are configurable (`RANGE_HORIZONTAL`, 0-127) via MIDI Control Center —
the defaults just happen to be what we captured. `Transport Mode` (globalParamId
32) must be set to `MIDI CC` or `Both` for these to go out at all (default is
`Both`, which matches what we saw).

## Injection test — what echoes back over USB, what doesn't

Rather than relying on physically pressing keys/panel controls (slow,
latency-prone round trip through chat), messages were injected directly into
`hw:0,0,0` with `amidi -S` while `amidi -d` listened on the same port
simultaneously. This works because the port is bidirectional — no separate
MIDI interface needed.

Result: **only Note On/Off get echoed back** over USB when injected as input.
Pitch Bend, Control Change (including the transport CCs above), and Channel
Aftertouch sent in produced **no output at all** — no echo, no visible
side effect over MIDI. Likely explanation: the device merges/thrus Note
messages specifically (useful for DAW-side note monitoring/layering), but
other message types are either not merged back over USB, or only affect
local state (LEDs, internal transport) with no MIDI-visible confirmation.

Practical implication for the rest of this project: **note-triggered
behavior (velocity curves, chord expansion, arp/seq note output) can be
fully scripted** via `amidi -S`/`amidi -d` without needing hands on the
hardware. **Panel-only state (Chord Mode via Shift+Hold, the Seq/Arp toggle
switch, the four Chord/CC knobs) has no known MIDI-input equivalent** — those
still require physical interaction, and their *effect* is only observable
through the resulting note stream once a key is pressed (see the Seq/Arp
switch and Chord Mode findings above — flipping/pressing them alone produces
no MIDI message; only the notes that result from playing while in that state
do).

## MIDI Identity Reply — confirms JSON fields against real hardware

Sent the standard Universal Non-Realtime SysEx Identity Request
(`F0 7E 7F 06 01 F7`) directly to `hw:0,0,0` via `amidi -S`. The device
replied immediately with a full Identity Reply — no guessing needed, this
is standard MIDI, safe to send to any device:

```
F0 7E 7F 06 02 00 20 6B 02 00 08 00 00 06 01 01 F7
```

Decoded per the MIDI Identity Reply spec:

| Field | Bytes | Value | Cross-check against `KeyStep37.json` |
|---|---|---|---|
| Manufacturer ID (extended, 3-byte) | `00 20 6B` | Arturia | matches `manufacturerId: "00206B"` exactly |
| Family code (LSB, MSB) | `02 00` | — | matches `familyId: "0200"` exactly |
| Family member code (LSB, MSB) | `08 00` | — | matches `alternatives[0].familyMemberId: "0800"` exactly |
| Software revision (4 bytes) | `00 06 01 01` | ≈ 1.1.6.x (LSB-first) | consistent with the actual firmware version, `1.1.6.579` (the trailing build number can't fit in a single 7-bit MIDI byte, so it's likely truncated/omitted here) |

This is a clean, fully protocol-level confirmation that the JSON pulled from
the Windows MIDI Control Center install is authoritative and directly
verifiable against the real device — not just inferred from static analysis
of the app binary. Worth doing this same Identity Request during/after an
actual firmware flash to see if the reported revision changes accordingly.

## Injected-note echo behavior

- Note On velocity echoes back **unchanged** (tested 0x01, 0x20, 0x40, 0x60,
  0x7F — all echoed exactly).
- Note Off velocity is **always normalized to `0x40`** on echo, regardless
  of what was sent (sent `00` each time, always got `40` back) — matches

  echo**, consistent with the "only Note On/Off get merged back over USB"

## Arturia SysEx message envelope — reverse engineered from MIDI Control Center binary

Since the earlier XOR/format guessing on the firmware file hit a dead end, tried a more
reliable route: **the app itself has to build these SysEx messages somewhere in its own
code**, so a raw byte search for the manufacturer ID (`F0 00 20 6B`) inside the actual
installed binary (not the compressed Inno Setup installer — that gave zero hits since
it's compressed; the real target is
`/mnt/c/Program Files (x86)/Arturia/MIDI Control Center/MIDI Control Center.exe`, which
is uncompressed) found one real code reference at file offset `0x4a0be8`.

Disassembled with capstone (x86-64) around that address
(`.venv` has capstone installed for exactly this). The function builds a SysEx message
into a caller-provided buffer as follows (`rcx` = destination buffer pointer):

```
offset 0        : 4-byte LE total length (internal wrapper field, not part of the wire SysEx bytes)
offset 4        : F0                      (SysEx start)
offset 5-7      : 00 20 6B                (Arturia manufacturer ID, extended 3-byte form)
offset 8        : caller-supplied byte    (from stack arg — likely family-related selector)
offset 9        : caller-supplied byte    (from stack arg — likely family-member-related selector)
offset A        : auto-incrementing sequence counter, byte, wrapped to a 7-bit-safe range
                  (global counter at a fixed .data address, incremented and masked with
                  `and eax, 0x8000007f` + sign-correction on every call — almost certainly
                  a per-message transaction ID so replies can be matched to requests)
offset B        : caller-supplied byte (r9 register arg)   — likely command/opcode
offset C        : caller-supplied byte (dl register arg)   — likely sub-command/param selector
offset D        : running checksum, byte, masked to 0x7F   (simple additive sum of the
                  payload bytes, computed during the packing loop below)
offset E..      : payload, bit-packed 7-in-8 encoding (see below)
end             : F7                      (SysEx terminator, appended after the payload)
```

**Payload packing (offset 0xE onward)** is the classic MIDI "7 data bytes → 8 SysEx-safe
bytes" scheme also used by several other manufacturers' bulk-dump formats: for each group
of up to 7 raw payload bytes, it emits 8 output bytes — the first 7 hold each source
byte's top 7 bits (`byte >> 1`), and the 8th byte accumulates the low bit of each of the
7 source bytes, one bit per position (`OR`ed into `[block+7]`, shifted left by the
in-group index). This guarantees every output byte stays within `0x00-0x7F`, which is
required for a byte to be legal inside a SysEx stream. **This is very likely the same
packing scheme used to embed the actual firmware image inside a firmware-update SysEx
transfer** — worth testing once we capture (or construct) a real firmware-update SysEx
session.

**Open questions / not yet empirically confirmed:**
- Exact semantics of the offset 8/9 bytes (family vs. family-member selector — best
  guess based on the Identity Reply's family/family-member codes `02 00` / `08 00`,
  but not yet confirmed against a live call site with known arguments).
- Exact semantics of offset B/C (command/sub-command opcode values for "get parameter" vs
  "set parameter" vs other operations) — these are register-passed arguments, so finding
  them requires tracing the *callers* of this function (not yet done) to see what
  constants get passed in for a real "get global parameter" call, rather than guessing.
- Whether the sequence-counter byte at offset A needs to match a specific value on reply,
  or is purely informational.

**Next concrete step for this thread**: find and disassemble the callers of the function
at `0x4a0be8` (in Ghidra rather than ad hoc capstone snippets, since this needs cross-reference/call-graph analysis) to pin down the real opcode values for a "get global
parameter" request, then construct and send one live against the hardware to confirm.

## SysEx opcode table — from Ghidra call-graph analysis

Used Ghidra headless (`analyzeHeadless -process ... -postScript find_callers.java`,
script kept in the session scratchpad, not the repo — it's a one-off analysis tool,
easily rewritten) to find and decompile all **17 callers** of the SysEx-header-builder
function (`FUN_1404a17b0`, VA `0x1404a17b0` in the installed
`MIDI Control Center.exe`). Each call site passes a literal or near-literal opcode as
its 2nd argument, which our earlier disassembly showed gets stored at message
offset `0xC` (see the envelope layout above). This directly answers the open question
from that earlier analysis: what are the real command byte values.

| Opcode | Payload size | Confidence | What it does |
|---|---|---|---|
| `0x16` | up to 32 bytes (dynamic) | **High** | Send firmware data packet, more packets follow. Confirmed via adjacent log string `"[HWTemplate] Send Next Packet [N] of size S"` and the fact the payload is read live from a stream object 32 bytes at a time. |
| `0x17` | up to 32 bytes (dynamic) | **High** | Same as `0x16` but the *final* packet of a firmware transfer — selected by a boolean "is this the last chunk" flag in the caller. |
| `0x52` | 35 bytes (`0x23`), fixed structured payload | Medium | Very likely a firmware-update **descriptor/begin** message sent once before the `0x16`/`0x17` packet stream — the payload is assembled field-by-field from a 6+-field struct (sizes matching typical "total length + version + checksum"-style firmware headers), not raw stream bytes like the packet messages. |
| `0x3a` | 35 bytes (`0x23`), fixed | Medium | Same payload size as `0x52` — appears twice in one caller (`FUN_14049ef80`), possibly a paired read-back/verify of the same descriptor structure, or the equivalent message for a different device/firmware family reusing this codepath. |
| `0x18` | 1 byte | Low-medium | Appears identically in two different callers (`FUN_14049f890` and one other), always with a 1-byte payload sourced from `param_1 + 0x70` — shape suggests a small status/ping-style message, not confirmed. |
| `0x19` | 3 bytes | Low | Single occurrence, 3-byte payload — plausibly a "get/set parameter" style message (3 bytes could be paramId + globalParamId + value), not confirmed. |
| `0x3b` | 3 bytes | Low | Occurs twice in the same caller with a 3-byte payload from a shared local buffer — same shape as `0x19`, not confirmed which specific operation. |
| `0x45`, `0x47`, `0x49` | 1-3 bytes | Low | Each occurs once; no distinguishing log strings found nearby. Payload sizes (2, 1, 3 bytes respectively) are the only clue so far. |
| `0x15` | 0 bytes | Low | Occurs with a null/zero data pointer and zero count — likely a bare command with no payload (e.g. a query/trigger with nothing to send, matching the pattern of the Identity Request we already tested live and confirmed works). |
| `2`, `3`, `0`, dynamic (`param_2`/`param_3`) | varies | Not resolved | Several call sites pass the opcode as a parameter of their *own* caller rather than a literal, meaning the real value is chosen even further up the call chain — would need one more level of caller-tracing to pin down. |

**Caveat**: this table is built from static analysis of the Windows app, not from
live captures against the hardware. `0x16`/`0x17` are the best-confirmed (independent
log-string evidence). The rest are structurally plausible but unverified — the
concrete next step is to construct and send one of the higher-confidence candidates
(e.g. `0x15` as a zero-payload probe, since we already know zero-payload SysEx like
the Identity Request is safe to send) and see what comes back.

Full Ghidra project + the analysis script are in the session scratchpad
(not committed — regenerable from the binary + `find_callers.java` in a few
minutes if needed again).

## Live opcode verification attempt — inconclusive, but resolved the family-byte question

Tried sending a constructed `0x15` (zero-payload) probe built from the reverse-engineered
envelope: `F0 00 20 6B 02 08 00 00 15 00 F7` (manufacturer ID, family=0x02, familyMember=0x08,
counter=0x00, payload-length=0, opcode=0x15, checksum=0x00). **No response** from the
hardware.

Rather than guess again blindly, traced this further in Ghidra:
- The two global bytes read by every caller of the envelope builder (`DAT_1414349fc` /
  `_DAT_1414349f0`, the family/family-member fields) are written by exactly one function,
  `FUN_140406150` — a device-identification resolver that `memcmp`s the connected
  device's name string against `"MiniBrute"`, `"MicroBrute"`, `"MatrixBrute"`, and
  `"MicroFreak"` only, throwing `"Cannot find Device called ..."` for anything else.
  **KeyStep 37 is not one of its branches.**
- Searched the entire binary for the literal string `"KeyStep 37"` (both ASCII and
  UTF-16LE) — **zero matches anywhere in the file.**

Conclusion: KeyStep 37 (and presumably other newer-generation devices) aren't identified
through hardcoded per-device name branches like the legacy Brute/Freak family. They're
handled generically, with `familyId`/`familyMemberId` parsed directly from the JSON
resource files (`KeyStep37.json`) we already pulled from the live install, then copied
into these same shared globals at runtime. This **confirms by elimination** that
`family=0x02, familyMember=0x08` (straight from `KeyStep37.json`'s `"familyId": "0200"` /
`"familyMemberId": "0800"`) are the correct values — there's no competing hardcoded
value anywhere in the binary. The lack of a response to the `0x15` probe therefore
points at the **opcode** or **counter/checksum handling** being wrong, not the
family/familyMember bytes. Next attempt should try a different candidate opcode (e.g.
one of the 1-3 byte-payload ones from the table above) rather than `0x15` again.

## Opcode `0x00` confirmed: reboot into bootloader mode

Grepped the existing Ghidra decompile output (already captured this session)
for bootloader/reboot-related strings and found:

```
FUN_140393000(uVar4,&local_88,2,"Prepare Hardware : Reboot the device...");
...
FUN_1404a17b0(&local_60,0,0,0);          <-- opcode = 0, zero payload
...
FUN_140393000(uVar4,&local_98,2,"Prepare Hardware : Reboot the device...OK");
```

**High confidence** (direct log-string evidence, same pattern that confirmed
`0x16`/`0x17`): **opcode `0x00` with zero payload reboots the device into
its firmware-update/bootloader USB personality** (PID `0x0291` per
`KeyStep37.json`). After sending it, the app waits ~5 seconds then polls up
to 5 times to reopen the device, presumably now enumerated under the
bootloader PID. This is a genuine software-triggered path into bootloader
mode — no physical button combo needed (the manual documents a button-combo
factory-reset, but nothing for firmware/bootloader mode, consistent with
this being purely software-triggered).

Full message to test: `F0 00 20 6B 02 08 <counter> 00 00 00 F7`
(manufacturer ID, family=0x02, familyMember=0x08, any counter byte,
payload-length=0, opcode=0x00, checksum=0x00).

**Live test result: negative.** Sent this exact message twice (with different
counter bytes) directly to `hw:0,0,0` — no re-enumeration under PID `0x0291`,
no response captured on a simultaneous listener, `lsusb` showed the device
unchanged throughout a 10s poll. A burst of `vhci_hcd: urb->status -104`
kernel log lines appeared right after sending, which looked promising at
first, but turned out to be a **red herring** — the identical pattern
appears earlier in `dmesg` at a timestamp with no SysEx activity nearby,
confirming it's just routine cleanup when `amidi -d`'s `timeout` wrapper
kills the listening process, not evidence of a device reset.

Most likely explanation: the decompiled caller function gates entry to the
reboot call behind `FUN_1404a0010(...)` — a call that runs *before* the
reboot opcode and looks like "open/find device" — succeeding first. There is
probably a session/handshake sequence the real app performs when it opens a
connection to the device that we haven't replicated, and the firmware may
simply ignore privileged commands like this one sent without that
established session, as a safety measure. Finding that handshake would need
more Ghidra tracing (of `FUN_1404a0010` and what precedes it) — but the
**already-planned real firmware-update capture (see below) will show this
whole sequence directly**, handshake included, which makes further blind
guessing here lower priority than just doing that capture.

## REAL firmware-update capture — ground truth from Wireshark/USBPcap on Windows

A genuine USB capture (`firmware-re/captures/keystep37_firmware_update.pcap`,
1.3MB) was taken on Windows using USBPcap while running an actual reflash
through MIDI Control Center, then analyzed here with `tshark`. This
**supersedes several static-analysis guesses below with real ground truth** —
noted inline where they conflict.

Wireshark's own USB-MIDI dissector reassembles SysEx messages automatically
(`tshark -r <file> -Y "usb.data_len>0" -V`, look for `[Reassembled data: ...]`),
which made this far easier than raw byte-counting.

### Device address / PID timeline

```
frame 2:     addr 1, VID:PID 1c75:0219   (normal mode, initial enumeration)
frame 660:   addr 5, VID:PID 1c75:0291   (bootloader/update mode - confirmed!)
frame 22518: addr 7, VID:PID 1c75:0219   (back to normal mode after update)
```
(`frame 22462, addr 6, VID:PID 1c76:0219` also appears — one digit off from
our device; almost certainly an unrelated USB device enumerating around the
same time, not investigated further.)

### Connection sequence (every time MCC connects, not update-specific)

1. Standard MIDI Identity Request/Reply, sent twice:
   `F0 7E 7F 06 01 F7` → `F0 7E 7F 06 02 00 20 6B 02 00 08 00 00 06 01 01 F7`
   (identical to what we captured live earlier this session — confirmed).
2. A long **GET-parameter loop**, reading essentially every device setting:
   - Request: `F0 00 20 6B <sessA> <sessB> 01 00 41 <globalParamId> F7`
   - Ack: `F0 00 20 6B <sessA> <sessB> 1C 00 F7` (short, immediate)
   - Reply: `F0 00 20 6B <sessA> <sessB> 02 00 41 <globalParamId> <value> F7`

   `sessA`/`sessB` were `7F`/`42` throughout this entire capture — constant
   for the whole session. **`0x41` = 65 decimal, exactly matching
   `KeyStep37.json`'s `deviceGlobalParametersId: 65`** — it's the paramId
   for the global-parameters container, not an opcode. `01 00` (request) vs
   `02 00` (reply) is the real request/reply discriminator.

   The exact sequence of `globalParamId` values requested (`08, 0b, 0c, 0f,
   09, 0e, 13, 11, 12, 0a, 15, 16, 17, ...` = `8,11,12,15,9,14,19,17,18,10,
   21,22,23,...` in decimal) is an **exact match** to the `globalFields`
   group ordering in `KeyStep37.json` (e.g. the "Sequence Settings" group:
   `[510→8, 513→11, 514→12, 517→15, 518→9, 516→14, 521→19, 519→17, 520→18,
   512→10, 522→21, 523→22, 525→23]`). This confirms beyond doubt that this
   loop is simply MIDI Control Center reading every setting to populate its
   UI on connect — **it happens on every connection, not just before a
   firmware update.**

### ⚠️ Correction to earlier static-analysis findings

The two bytes at message offset 8-9 (which static analysis of the MCC
binary suggested were a "family" / "family-member" selector, guessed as

### The actual update trigger (not the parameter-read loop)

After the entire parameter-read loop completes, exactly one more message is
sent before the reboot:

```
F0 5A 57 6E 28 3C 4E 51 F7
```

**`5A 57 6E 28 3C 4E 51` is byte-for-byte identical to `KeyStep37.json`'s
`extraParameters.productKey: [90, 87, 110, 40, 60, 78, 81]`.** This resolves
the earlier open question about what that key is for — it's sent as a raw
SysEx payload (notably *not* wrapped in the standard manufacturer-ID
envelope) immediately before the device reboots into bootloader mode. This
looks like a simple product-specific unlock/authentication payload for the
firmware-update trigger, not a cipher key applied to the firmware image
itself (the earlier XOR-decode attempt against the `.led` file was the
wrong theory).

Immediately following this message, `lsusb`-equivalent activity shows the
device disappearing from address 1 and reappearing at address 5 under PID
`0x0291` — the actual bootloader-mode reboot, confirmed live.

### The actual firmware transfer protocol (bootloader mode) — fully solved

Once re-enumerated as address 5 / PID `0x0291`, standard USB descriptor
requests happen (control endpoint `0x80`), then:

1. **`productKey` sent again**, this time to the bootloader-mode device:
   `F0 5A 57 6E 28 3C 4E 51 F7` (frame 701) — so this unlock payload is sent
   twice: once to the app-mode device just before the reboot trigger, and
   again to the freshly-enumerated bootloader-mode device before it will
   accept a firmware transfer.
2. **Device replies `F0 51 F7`** — a bare one-byte status/ack code.
3. **The actual firmware chunks stream immediately after**, on bulk OUT
   endpoint `0x01` (a *different* endpoint than the app-mode MIDI interface's
   `0x02`/`0x81` — bootloader mode has its own USB-MIDI endpoint layout).
4. **After the last chunk, device replies `F0 77 F7`** — another bare
   one-byte status code, presumably "transfer complete/success" (`0x77`
   vs. the unlock ack's `0x51` — different status values for different
   events, but the exact code→meaning mapping wasn't tested further, e.g.
   we don't know what a *failure* status code looks like).
5. Device disappears and re-enumerates back to PID `0x0219` (normal mode) —
   confirmed via device address 6→7 transition (address 6 briefly showed an
   anomalous VID `0x1c76` instead of `0x1c75` in one descriptor read, almost
   certainly a transient/garbled read during the reset, not a different
   device — address 7 cleanly shows `0x1c75:0x0219` right after).

**The firmware-chunk transfer format itself is dramatically simpler than the
app-mode "arturia_v2" envelope** (no manufacturer-ID header, no session
bytes, no opcode, no checksum, no 7-in-8 bit-packing):

```
F0 <raw bytes, straight from the .led file> F7
```

That's it. Each chunk is `F0` + a slice of the `.led` file's **raw hex-ASCII
text** (not decoded — the literal ASCII characters `'0'`-`'9'`/`'A'`-`'F'`)
+ `F7`. This works with zero encoding overhead because the `.led` file's
content is already restricted to hex digit characters, all of which are
valid 7-bit SysEx data bytes (0x00-0x7F) — no bit-packing is needed the way
it is for arbitrary binary payloads in the app-mode protocol.

**Verified empirically, not inferred**: extracted all 10,693 chunk payloads
from the capture in frame order, stripped the `F0`/`F7` framing, concatenated
them, and the result is **byte-for-byte identical** to
`og_firmware/keystep37_Firmware_Update_1_1_6_579 (1).led` — same 234,280
bytes, exact match, confirmed with a direct binary comparison
(`extracted == original` → `True`). This means we now have a **fully
verified, working understanding of the exact wire format used to flash this
device** — not a guess.

Chunk size distribution (10,693 total chunks): 10,517 chunks of 22 raw
bytes, 109 of 18 bytes, 66 of 14 bytes, 1 of 20 bytes — the small tail sizes
are an artifact of USB-MIDI's fixed 4-byte packet framing (3 payload bytes
per packet) not always dividing evenly into a SysEx message length, not a
deliberate variable chunk-size scheme. 10,517×22 + 109×18 + 66×14 + 1×20 =
234,280 — matches the file size exactly.

### Base address confirmed via real disassembly, not assumed

Earlier this session (during the live opcode probing) we'd tentatively
guessed `0x08000000 + 0x14` as a starting point without verifying it. Did
that properly this time:

- Wrote a script to scan the decoded binary for long runs of consecutive
  4-byte-aligned words that are all odd (Thumb bit set) and share the same
  high address bits — the signature of either a vector table or an
  absolute-address jump table.
- Found a strong candidate at file offset `0x90EC` (37100): ~26 consecutive
  entries all in the `0x0800Cxxx` range, mostly repeating `0x0800CC63` with
  a handful of distinct targets (`0x0800CC55`, `0x0800CD2D`, `0x0800CD33`,
  `0x0800CFD1`).
- **Verified, not assumed**: disassembled at each target address under the
  hypothesis `base = 0x08000000` (i.e. `file_offset = target - 0x08000000`).
  All 5 produced clean, coherent ARM Thumb instructions (register loads,
  comparisons, branches — real compiled code, not noise). This confirms
  `0x08000000` is the correct load base with actual evidence, matching the
  standard STM32 flash-at-zero-offset convention (consistent with this
  project's STM32 assumption, but now independently confirmed rather than
  taken on faith).
- No genuine Cortex-M interrupt vector table (SP + reset handler pair) was
  found anywhere in the file — searched systematically, no run of ≥6
  plausible odd-address entries preceded by a valid RAM-range stack pointer
  exists. Likely explanation, consistent with this project's own safety
  docs: **the vector table lives in the protected bootloader region, not
  in this app-only `.led` image** — this file is pure application code
  starting after a small 20-byte Arturia-specific header, with no vector
  table of its own.

### Strong lead: likely found the GET-parameter handler itself

Traced the one caller of `FUN_0800cc14` (the candidate ring-buffer
receiver): **`FUN_08001f68`** (424 bytes). Decompiling it shows a message
dispatcher that branches on the first byte of an incoming buffer, and
critically:

```c
if (uVar8 == 0x41) {
    puRam080020fc[7] = 0;
    *(ushort *)(puRam080020fc + 4) = (ushort)*(byte *)(iRam08002100 + uVar5 + 0x3c);
}
```

**`0x41` = 65 decimal — exactly `KeyStep37.json`'s `deviceGlobalParametersId`,
confirmed earlier this session from real captured wire traffic.** `uVar5`
above is `param_2[9] & 0x7f` — and position 9 is *exactly* where
`globalParamId` sits in the real captured wire format
(`F0 00 20 6B <sessA> <sessB> 01 00 41 <globalParamId> F7`, 0-indexed from
`F0`). The code then reads a byte from `iRam08002100 + globalParamId + 0x3c`
— very likely **the actual in-RAM parameter value table**, indexed
directly by the same `globalParamId` scheme confirmed via live protocol
testing.

This is a genuine convergence of the Goal 1 (protocol) and Goal 2 (firmware
code) work — found by tracing *from* the confirmed wire protocol *into* the
code, rather than guessing blind, which is exactly the right method for
"no inference" mapping. Checked whether the same RAM table
(`iRam08002100`) is written anywhere else (which would be the unconfirmed
SET-parameter path) — Ghidra's static reference search only shows this one
access. Likely means the write path (if it exists elsewhere) computes the
address differently and isn't caught by a simple reference search — not

likely the firmware's control-state reporting/handling logic for these
three physical controls, including **the Seq/Arp Mode encoder that
selects the 8 arp modes** — found by grounded tracing from a confirmed
protocol constant, not guessed.

**Not yet resolved**: exactly what `func_0x0800cd98` (the seqarp/octp
handler) does with the value. Tried disassembling directly at that
address and at `FUN_0800cd2a` (the resolved octm-path call target) —
both landed on ambiguous/garbage results (misaligned instructions,
Ghidra reporting a 1-byte "function" with an impossible infinite loop
using uninitialized registers). This is a real, informative negative
result: it strongly suggests these targets are entries in a **function
pointer table** (a per-control descriptor/dispatch structure, similar in
spirit to the vtable-style patterns seen in the Windows companion app),
not plain inline code at that byte offset — which naive linear
disassembly can't resolve without first identifying and typing the table
itself. That's a real, different technique (structural table mapping,
not more disassembly-address-guessing) needed to go further here, and
it's not done.

Also not yet found: where the resulting "current arp mode" state gets
*stored*, and where *that* storage location gets *read* by the actual
note-generation code for each of the 8 modes — that read site is where
the real Pattern-mode generator and chord-trigger hook would be found.
That's the concrete next step, not yet done.

### Third breakthrough: found all 48 real switch dispatches in the binary

Ghidra's own switch-recognizer only caught 1 of these (3 cases). Scanned
the **entire firmware for `TBB`/`TBH` instructions directly** (Thumb-2's
dedicated table-branch opcodes, used by the compiler for every switch
statement) using capstone — found **48 real switch dispatches**, then
parsed each one's preceding bounds-check (`CMP Rn, #N`) to get exact case
counts. This is comprehensive and exhaustive — every switch in the binary,
not just what Ghidra happened to notice.

The strongest candidate for "8 arp modes" by case count (`0x08002174`,
exactly 8 cases) turned out to be something else, but something
genuinely useful: a clean **control-ID ↔ compact-index converter** for
the 8-button transport/octave group. Decoding both the forward and
reverse mapping tables:

```
0x55 (hold)      <-> index 0
0x56 (shift)     <-> index 1
0x10 (octm)      <-> index 2
0x11 (octp)      <-> index 3
0x67 (tap)       <-> index 4
0x57 (record)    <-> index 5
0x59 (btnStop)   <-> index 6
0x5a (btnPlay)   <-> index 7
```

This independently confirms 6 more control IDs from `KeyStep37.json`
against real firmware code (hold, shift, tap, record, stop, play — on top
of the octm/octp/seqarp already confirmed in the earlier breakthrough).
**`seqarp` (18) is not in this particular table** — it belongs to a
different control group, confirming the earlier hypothesis that the
Seq/Arp Mode encoder is handled separately from this momentary-button
group. A second small nearby table (4 cases: ids `0x63,0x64,0x65,0x66` =
99-102, i.e. `knobRate`=102 and 3 sequential neighbors) looks like the
analogous converter for the 4 generic CC knobs.

Checked the remaining candidates systematically (batch-disassembled every
distinct jump target for each):

- **`0x800ef90`** (8 cases): each case reads a byte and does `sdiv` against
  small multiples (÷1,÷2,÷4,÷8 via shift amounts). **Very likely the Time
  Div selector** — the manual states Time Div has exactly 8 settings, and
  these look like clock-division ratios.
- **`0x800e494`** (8 cases): each case just returns a small constant —
  `0x1e0(480), 0x78(120), 0x3c(60), 0x140(320), 0xa0(160), 0x50(80),
  0x28(40), 0xf0(240)`. These are consistent multiples/ratios of a base
  period (480 ÷ 2,3,4,6,8,12,17ish) — **corroborates the Time Div
  hypothesis** as a period-lookup table (a second, related function to
  the one above, not a duplicate — plausible as "convert Time Div setting
  to an actual tick period").
- **`0x800af84`** (10 raw entries, 8 distinct targets) — **the strongest
  arp-mode candidate found**: each case calls a genuinely *different*
  subroutine (`0x800ac9e, 0x800adf8, 0x800ae42, 0x800aee6, 0x800af20,
  0x800ac42, 0x800af4c, 0x800ac8a`), all tightly clustered in a ~0x300-byte
  region. Disassembled all 8:
  - `0x800ac42` is a **2-byte no-op stub** (`bx lr` immediately) — a
    "do nothing extra" mode.
  - Several others (`0x800ae42`, `0x800aee6`, `0x800af20`, `0x800af4c`)
    each contain their own small internal branching, but all funnel into
    calling **the same shared handler, `0x800ac8a`**, for their default
    case.
  - `0x800ac8a` itself contains **another nested switch** (`0x800ac94`,
    7 cases — one of our other catalogued candidates) — a second layer of
    dispatch.
  - `0x800adf8` is the clear outlier: distinct logic, no fallback to the
    shared handler, calling two functions not seen anywhere else
    (`0x8015220`, `0x800b1a6`).

  This shape — several similar modes sharing core logic, a couple of
  genuinely distinct special-cased ones, plus a no-op — is structurally
  a strong match for the 8 arp modes (several of Up/Down/Inclusive/
  Exclusive plausibly share simple traversal logic; Random/Walk/Pattern
  plausibly need distinct logic).

  **Traced one level up, honestly inconclusive**: `0x800ac8a`'s only
  statically-found caller (besides itself) is `FUN_0800b0bc`, which reads
  more like a **general note/MIDI-event router** (branches on an event-type
  parameter against the value 3, checks a MIDI-style `0x80` velocity/status
  bit) than an arp-mode-specific function. Traced one level further to its
  own caller (`FUN_080155a4`) — that bottoms out in generic low-level event
  plumbing with no clear, unambiguous link back to the confirmed `seqarp`
  control ID. **`0x800af84` is a strong, well-reasoned hypothesis for the
  arp-mode dispatch, not a proven one** — the exact chain from "seqarp
  encoder value" to "this dispatch table" could not be established with a
  single unbroken static trace, because the intervening calls are indirect
  (through function pointers / computed addresses) in a way that resists
  the disassembly and cross-reference techniques used here.

- Remaining unchecked candidates (`0x8002582`, `0x8009f64`, `0x800a1da`,
  `0x800ac94` (now identified as the nested sub-dispatch inside
  `0x800ac8a` above), `0x800b85a`, `0x800d744`, `0x800e09e`, `0x8010be8`,
  `0x8010d04`, `0x8010e48`, `0x8013b7c`, `0x801419e`, `0x8014406`,
  `0x8015f6e`, `0x8016a3c`, `0x8016fea`) were batch-disassembled but not
  individually deep-dived — several look like MIDI-status-byte or
  hardware-register-flag dispatchers based on their case bodies (e.g.
  `0x8010be8`/`0x8010d04`/`0x8010e48` all touch the same `+0x400/0x401/0x402`
  struct offsets, suggesting a shared 3-field record, possibly per-note or
  per-step data), not obviously arp/chord specific.

### Correction: `FUN_08013482`'s real boundary is `0x08013492` — clean decompile obtained

The corrupted decompile above (`NMI`/`Reset`/`UsageFault` names, implausible
addresses) had a findable root cause, not just "decompiler unreliability in
general": **Ghidra's auto-analysis put the function's entry point 16 bytes
too early.** Verified by raw `capstone` disassembly (`.venv` has it) of the
surrounding bytes: address `0x08013482`-`0x08013491` decodes into a
repeating `asrs rX,rY,#N` / `movs r0,#0` pattern — the classic look of
arbitrary data forced through a Thumb disassembler, not real code — while
`0x08013492` is a completely ordinary, sane function prologue
(`push {r4,r5,r6,lr}; sub sp,#0x20; mov r5,r0; ldr r3,[r0,#0x18]; ...`).
A real control-flow trace (BFS over every branch/call target and
fallthrough from `0x08013492`, not just linear sweep) confirms the entire
reachable instruction set for this function spans `0x08013492`-`0x0801378c`
(228 real instructions), with a 9-word literal pool immediately after at
`0x08013790`-`0x080137b0` — which ends exactly where the *next* real
function begins (`0x080137b4`, confirmed both by its own sane prologue
and by the raw word bytes matching `push {r3,r4,r5,lr}; mov r4,r1`
byte-for-byte). This 16-byte boundary error is exactly the kind of mistake
that produces garbage decompiles — Ghidra's decompiler was doing its best
with a function object that started in the wrong place.

Re-imported the firmware, deleted Ghidra's wrong-boundary function object,
manually created the function at `0x08013492`, and re-ran full analysis
(script: `fix_and_decompile.java`, scratchpad). The resulting decompile
(renamed `FUN_08013492_ccnotify`) is dramatically cleaner — no more
ARM-exception-name artifacts anywhere:

```c

{
  ...
  if (*(int *)(param_1 + 0x18) == 0) {

LAB_080134bc:

      local_2c[0] = local_18;
      ... FUN_0800d490(*DAT_080137ac, local_2c[0]);   // <-- queues/sends the 3-byte MIDI message

    }
```

**This confirms the hypothesis directly, not just circumstantially**: the
`0xb0 | ...` construction is the literal MIDI status byte for "Control
Change, channel 1" — the exact same status byte (`B0`) seen at the start
of every single CC message captured live all session. This function
genuinely **builds and queues a 3-byte MIDI CC message**
(`local_2c[0]` = packed status/CC-number/value word), based on a
changed-value check (`param_1+4` = last-known value, compared implicitly
via the surrounding branches) for whichever physical control's state
struct is passed in as `param_1`. It is the CC-telemetry notifier, now
confirmed by structure, not just by name.

**The `0x20001120` RAM-subscriber address is directly referenced from
inside this function's own literal pool** (`*DAT_080137a8` resolves to
`0x20001120`, dereferenced and passed as the first argument to
`FUN_0801a048` with a literal `5` as the second argument) — tying this
function concretely to the subscriber-registration mechanism traced
earlier from the Test-20 dispatch path. This is the strongest link found
so far between "physical control changes → this notifier" and "Test 20's
subscriber table," though the exact semantics of `FUN_0801a048`'s
argument `5` aren't decoded yet.

**Still genuinely unresolved, flagged honestly rather than papered over**:
- `unaff_r4`, `unaff_r6`, `unaff_r7`, `extraout_r2` persist even after a
  full re-analysis pass — these registers are read by the function without
  ever being written inside it, meaning either (a) the real calling
  convention passes more live inputs than the visible 3 stack/register
  parameters (uncommon but not impossible for hand-tuned firmware code),
  or (b) this function has multiple real entry points beyond the one
  `push`-based prologue (entered via direct branch from elsewhere with
  registers already populated by the caller, rather than solely via `bl`).
  Distinguishing these needs finding every `bl`/`b` reference to
  `0x08013492` and inspecting caller context — not yet done.
- One literal (`uRam08013770`, i.e. `0x4b0fe7b2`) doesn't resolve to a
  sane flash/RAM pointer, unlike every other literal in this function's
  pool. **Ghidra's own independent re-analysis hits the exact same
  ambiguity** (same `uRam08013770` unresolved-global fallback in its own
  decompile) — cross-confirming this is a genuine oddity in the binary
  layout at that address, not an artifact of one analysis method. Given
  the ambiguity is isolated to a single value used only once (not the
  overall function structure, which is now solid), this is logged as an
  open item rather than force-fit into an incorrect explanation.

**Practical significance for Goal 2**: this is the deepest and most
concrete evidence yet that the confirmed CC-telemetry mechanism (Test 20 →
subscriber registration at `0x20001120` → this notifier building a real
`0xb0`-prefixed MIDI CC message) is a single, coherent, now-largely-mapped
pipeline — not several independent guesses. The next step toward the
actual arp-mode/chord-state RAM location is finding every caller of
`FUN_08013492_ccnotify` (which `param_1` struct gets passed for which
physical control), which would directly identify the per-control state
structs this whole session's confirmed CC numbers correspond to in RAM.

## Boot-population investigation: interrupt-vector hypothesis tested and ruled out — genuine static-analysis floor reached

Pushed on the "how do these handlers actually get invoked" question one
level further: since `0x08013492`'s address provably never appears as raw
data anywhere in this 117KB image (established earlier via exhaustive
byte search), it categorically **cannot** be populated into any RAM table
via a boot-time `memcpy`-style copy from a flash-resident source table —
the source bytes for such a copy would themselves have to contain the
value somewhere in this image, and they don't, anywhere.

The next most plausible explanation was that this function (or a small
trampoline branching to it) is installed as a **hardware interrupt
handler** (timer tick or GPIO/EXTI pin-change, both natural fits for
polling/servicing physical controls) — interrupts are dispatched by the
CPU directly from a vector table, never via a `bl`/`blx` anywhere in the
code, which would fully explain the total absence of a static caller.
Tested this directly: scanned the **entire** 117KB image (not just the
file head, which is all that was checked earlier this session) for any
vector-table-shaped run of data — a plausible Cortex-M stack pointer
(`0x2000_0000`-`0x2003_0000` range) immediately followed by ≥10
consecutive plausible Thumb-bit-set flash addresses. **Zero candidates
anywhere in the file.** This is consistent with, and reinforces, the
earlier finding that this app-only `.led` image carries no vector table
of its own (it lives in the protected bootloader region) — and since the
target address doesn't exist as raw data at all, it also can't be an
entry in a vector table regardless of where that table lives, closing off
this hypothesis on the same grounds as the table-copy one above.

**Every static addressing mechanism available to this project has now
been tried and ruled out** for how this class of handler gets called:
direct branch (`bl`/`blx`/`b`, whole-binary scan), stored absolute pointer
(either Thumb-bit state, any file offset), `TBB`/`TBH` jump-table offset
(all 48 in the binary), `movw`/`movt` split-immediate construction, and
now interrupt-vector-table entry. This is a genuine floor for static
analysis on this specific question, not a "try one more technique" gap —
reached through actual elimination, not assumption. The address must be
constructed via runtime register arithmetic from a base that isn't itself
a discoverable constant (e.g. computed from a RAM value set up through a
longer chain this session hasn't traced, or a genuinely different
addressing scheme not yet conceived of).

**Honest recommendation**: closing this specific gap with confidence
would need either live SWD/debugger tracing (explicitly out of scope for
this project — "not interested in opening the case") or a materially
larger investment than anything tried so far: full symbolic/concrete
execution from reset with simulated peripheral memory-mapped I/O (briefly
noted as a possibility during the earlier `angr` work, and assessed there
too as "a materially bigger undertaking than the tooling upgrade tried
here" — that assessment still holds, now with considerably more evidence
behind it). Recommend treating the caller/dispatch-mechanism question as
closed for pure static analysis at this point, and redirecting any
further Goal 2 effort toward angles that don't depend on resolving it —
e.g. continuing to characterize what's *reachable* (like the sequencer
step-data engine and the CC-notifier's own internals, both now
well-mapped) rather than how it's *reached*.

## Arp-engine architecture: found a real vtable/OOP dispatch system — the actual explanation for the "no static caller" wall

Went back to the `0x800af84` arp-mode dispatch candidate (found earlier
this session, never fully decompiled) rather than re-attempting the
already-exhausted "find the caller" search. Decompiled the outlier case
handler `0x0800adf8`, its callees (`0x0801521e`, the `0x0800b1a6`+
cluster), and the shared handler `0x0800ac8a`/`0x0800affc` properly via
Ghidra (creating function objects where none existed, same technique
that worked for the CC-notifier fix). This produced the clearest picture
yet of how the arp/pattern engine is actually built:

**It's a small object-oriented dispatch system implemented in C.**
`FUN_0800affc` and `FUN_0800ac8a` both call through **function-pointer
slots inside a per-instance struct**, not fixed addresses:

```c
(**(code **)(*(int *)(param_1 + 0x214) + 8))();      // vtable slot +0x08
pcVar3 = *(code **)(*(int *)(param_1 + 0x214) + 0x28); // vtable slot +0x28
pcVar3 = *(code **)(*(int *)(param_1 + 0x214) + 0x30); // vtable slot +0x30
(*(code *)**(undefined4 **)(param_1 + 0x210))(...);    // a second, separate callback pointer
```

**This directly and completely explains why no static caller could be
found for any of these handlers** (the CC-notifier, the sequencer setter,
and presumably each mode-specific arp handler too): they're never called
by address at all in the compiled code. They're *assigned* into an
object's vtable struct (at `param_1 + 0x214`) at some point — almost
certainly when a mode/control is selected — and all the generic engine
code thereafter just calls "whatever's currently in slot N." A flat
`bl`/branch-target search was always going to come up empty for this
kind of code, regardless of how much more of it got searched. This isn't
a new limitation — it's the actual mechanism behind the wall documented
in the last two sections, now identified concretely instead of just
demonstrated by elimination.

**Confirmed structural details, from clean decompiles**:
- `param_1 + 0x1fc` (byte) and `param_1 + 500`/`0x1f4` (word) are both
  **state fields**, driving a small state machine (states 1-5+ seen so
  far: 2/3/4/5 each set by a dedicated tiny "enter state N" function —
  `FUN_0800b16c`→2, `FUN_0800b196`→3, `FUN_0800b1c4`→4, `FUN_0800b1da`→5 —
  each storing its own state-specific fields before calling one of two
  shared "commit" functions, `FUN_0801524c`/`FUN_0801525a`).
- Those two "commit" functions build/register what looks like a
  **hardware timer or DMA descriptor**: fixed fields `0x10, 0, 0x80,
  0x100, 0x400, 0, 0` written into a small struct, a classic
  self-referencing/circular-list initialization (`*(int*)base = base`),
  then `FUN_08004120(base)` (registration call) and a parent↔child
  back-pointer link (`self->child = base; base->parent = self`) — highly
  consistent with **scheduling the next arp/step timing event via a
  hardware timer**, matching this project's expectation that arp/seq
  timing is interrupt-driven.
- `FUN_0800b1f0` is a plain **struct initializer** with no branches:
  `note=0x3C (60, middle C), note2=0x3C, field+4=0x2000, flags@8/9/0xa=0`
  — a concrete default-state record for a note/step.
- `FUN_0800affc` indexes into a **16-byte-stride array** at
  `param_1 + ((value & 0x7f) + 0x10) * 0x10 + 4` — the same stride already
  found in the sequencer's step-storage engine (see above). Strong
  evidence the arpeggiator's "currently held notes" pool and the
  sequencer's step array are the same kind of underlying structure
  (plausibly literally shared code/layout), not coincidentally similar.

**One candidate for the actual per-mode vtable array, flagged honestly as
weak/unconfirmed**: scanned the whole binary for clusters of ≥4
consecutive valid Thumb-pointer-shaped words (same technique that ruled
out an interrupt vector table earlier, with a much lower run-length
threshold this time). Found `0x0801bbf4`: **exactly 8** distinct,
nonzero, valid-looking pointers in a row — a suggestive match for "8 arp
modes" purely by count, sitting inside a tight cluster of 3 other
similar-shaped tables within ~500 bytes. Checked its 8 targets' actual
disassembly for a consistent "mode implementation" shape (which would
raise confidence considerably): **inconclusive** — they don't show a
clearly parallel structure, and at least one entry (`0x080041e4`)
disassembles into non-code-looking garbage, suggesting this may be (at
least partly) a coincidental run of valid-looking bytes rather than a
genuine function-pointer table. No reference to this address (or any
address within ~0x260 bytes of it) was found anywhere in the binary
either, consistent with the same "computed, not literal" addressing
pattern seen everywhere else. **Logged as a lead worth revisiting with a
different technique, not a finding to build on.**

**Net assessment**: this round did not find "the Pattern-mode function"
by address, but it did find the actual *shape* of the problem — this is a
real vtable-based dispatch architecture, and the productive next search
(if pursued) is for **who writes to `object + 0x214`** (assigns a mode's
vtable into the generic engine object) rather than continuing to search
for call targets, which was always going to be structurally invisible
for this kind of code.

## Cross-version comparison: firmware 1.0.4.179 vs. 1.1.6.579

User supplied an older firmware file (`og_firmware/keystep37_Firmware_Update_1_0_4_179.led`,

- **Address-independent content comparison** (searching for exact byte
  sequences from known functions, cut short before any embedded

  mapped this session:

|---|---|

**Interpretation**: every real, confirmed structure from this session's
work (the whole arp-engine vtable/dispatch architecture, the CC-notifier,
the sequencer engine) exists **byte-identical** in the older firmware,
just shifted by a small, smoothly-accumulating offset consistent with
ordinary relinking (something else earlier in the binary changed size,
shifting everything after it slightly, with the shift growing the further

the arp/pattern engine code examined this session has changed across at
least two real firmware releases.** Practical implications:
- Whatever produced the ~1KB total size difference between 1.0.4.179 and
  1.1.6.579 is very likely elsewhere in the binary (a different

  of a "here's what changed for Pattern mode between versions" hotspot to
  exploit.
- The already-weak `0x0801bbf4` vtable candidate is now **less** credible,
  not more: a genuine function-pointer table referenced by running code
  should still exist as recognizable content in another real build of the
  same firmware family, and this one doesn't — consistent with it being
  linker/alignment debris that coincidentally looked like valid pointers,
  as already suspected from its inconsistent-looking targets.
- This cross-version technique (content search with `bl`-immediate-safe
  prefixes) is fast and reusable — worth applying again if a future
  firmware version is ever obtained (especially one release-noted as
  changing arp/sequencer behavior specifically, which would make this
  same comparison far more likely to land on the actual target code).

## Chord-trigger investigation, part 1: found the real dispatch entry, corrected an earlier boundary error, found the actual toggle logic

First real progress on the chord hook, following the unexploited lead
from earlier this session: `KeyStep37Test.json`'s CHORD test uses `0x69`
(105, confirmed Chord CC) as a literal command byte. Searched the whole
binary for `cmp`/`subs`-style immediate compares against `0x69` — found
**exactly one**, at `0x08001ee2`.

### Correction to the FUN_08013482/FUN_08013492 boundary work above

Tracing this led to a direct correction of the earlier CC-notifier
boundary fix. The containing function (real entry `0x08001edc`, another
address Ghidra's default analyzers never boundary-marked) decompiles
cleanly:

```c
void FUN_08001edc_chordtest(undefined4 param_1, undefined4 param_2, int param_3, uint param_4)
{
  if (param_3 == 0x69) {
    if (param_4 == 0) { FUN_08001ef6(); return; }         // chord OFF
    local_14 = *DAT_08001f34 & 0xffffff;
    func_0x080094c8(DAT_08001f38, 0, local_14);            // chord ON
  } else {
    // generic path for every other control ID, via FUN_08002108 (a
    // *different* converter, reusing the same iRam08002100/iRam080020fc
    // globals confirmed as the live parameter-value table much earlier
    // this session — good cross-confirmation this is the right neighborhood)
  }
}
```

This is a genuine, direct hit: `param_3` is the control ID being
processed, and `0x69` gets its own special-cased branch, separate from
the generic per-control path — consistent with `chord` having no declared
numeric control ID in `KeyStep37.json` (confirmed much earlier this
session), so the firmware itself has to special-case it too.

Following `func_0x080094c8`'s disassembly (`FUN_08001ef6`, the OFF path,
also calls this same function) turned up a real `bl` instruction at
`0x080094ee`: **`bl #0x8013482`** — a direct static call to
`0x08013482`. This is a **correction to earlier work**: that address is
exactly the one this session previously concluded was unreachable
"leading garbage" before the CC-notifier's true prologue at `0x8013492`.
Re-examined properly: those 11 bytes (`asrs`/`movs r0,#0` ×4) **are**
real, executed code — just functionally inert filler/padding that leaves
no register in a state anything later reads meaningfully — not
unreachable data as concluded before. **The real linked entry point for
the CC-notifier is `0x08013482`, not `0x08013492`**, and a whole-binary
scan for `bl`/`blx` targeting `0x08013482` specifically finds **exactly
one** static caller: this exact call site. The "zero static callers,
must be indirect" conclusion from earlier was an artifact of searching
for the wrong address, not a real architectural wall for this specific
function — a useful, humbling reminder to double-check "unreachable"
conclusions before generalizing from them, and now corrected.

### What the chord ON/OFF handler actually does — and what it doesn't

`func_0x080094c8`/`0x080094ee` turned out to be two entry points inside a
much larger function (real entry `0x08008fb4`-ish region, not fully
boundary-fixed — 331 reachable instructions traced via raw capstone
CFG-walk) built around a computed jump table at `0x080090ec`. That table
is **the same one already documented earlier this session** under "Goal 2
foundational work" (file offset `0x90EC`, ~26 entries, mostly repeating
`0x0800CC63` with a handful of distinct targets) — good independent
cross-confirmation both discoveries are looking at the same real
structure.

The shared tail both chord ON and OFF paths land in:
```
adds r2, r4, r5                  ; r5 = per-item index
ldrb.w r3, [r2, #0x4d]            ; read record[index].flags
and/orr r3, r3, #0x10             ; clear (AND ~0x10) or set (ORR 0x10) one bit
strb.w r3, [r2, #0x4d]
b #0x80090ac                      ; back into a loop bounded at r6<=7
```
The governing loop (`cmp r6, #7; bhi ...`) bounds exactly **8** iterations
— matching the already-confirmed 8-button transport/octave converter
table (hold/shift/octm/octp/tap/record/stop/play) exactly. Chord is
handled as a **special-cased 9th member** alongside that group (its
`0x69`/105 value doesn't fit that table's 0-7 index range), with its own
dedicated tail rather than participating in the loop itself.

**Honest scope of this finding**: this is **state bookkeeping and
diagnostic-telemetry plumbing for the Chord button's press/release** —
toggling a flag bit and notifying the CC-notifier (confirming, concretely
now, why pressing Chord in Test 20 produces `B0 69 01` telemetry). **It
is not the actual chord note-expansion logic** (the code that turns one
held key into a 3-note triad). That almost certainly lives in the
note-processing/MIDI-output path, checking whatever this flag toggles,
not in the button-handler code examined here.

**The concrete lead this hands off**: bit `0x10` at struct offset `+0x4d`
of a per-item record is a strong candidate for the actual "chord mode
enabled" flag (set/cleared by exactly the code that fires on Chord
button press/release). **Not yet done**: searching for code that *reads*
this same bit (`ldrb`/`ldrb.w ... , #0x4d` followed by a test against
`0x10`) in the context of note-on handling — that would be the direct
route to the real chord-trigger hook, and is the natural next step for
this thread.

## Chord-trigger investigation, part 2: found the actual note-output/voice loop

Direct follow-up on the flag-read search above. Searched the whole
binary for `ldrb`/`ldrb.w` reads at the exact struct offset `+0x4d` (the
flag the chord button toggles) — **13 hits**. 8 are inside the
already-mapped button dispatcher from part 1. The other **5 are in
completely different regions** (`0x08010xxx`, `0x08018xxx`) — real,
independent evidence this same offset gets read somewhere in genuinely
different code, not just echoed back to the same handler.

Three of those five (`0x080107cc`, `0x080185ce`, `0x080186c8`) sit inside
what turned out to be **the actual MIDI note-output construction path**:

```
ldrb.w r3, [fp, #0x4d]        ; read the flag
cbz    r3, #<skip>            ; skip this voice slot if not set
ldrsb.w r0, [fp, #0x4e]       ; velocity, from the field right next to the flag
and    r3, r8, #0xf
orr    r3, r3, #0x90          ; 0x90 = MIDI Note-On status, channel from r8
strb.w r3, [sp, #imm]         ; build a literal 3-byte Note-On message on the stack:
strb.w r4, [sp, #imm+1]       ;   status, note, velocity
strb.w r0, [sp, #imm+2]
```

The two occurrences at `0x080185ce`/`0x080186c8` are ~250 bytes apart and
structurally identical, each handling a **different voice-slot index**
(register `r7` vs `sl`/r10) inside what's clearly a **polyphonic
voice on/off dispatch loop** — the surrounding code (fully disassembled,
`firmware-re/` scratchpad) also builds a matching **Note-Off** message
(`0x80` status, fixed velocity `0x40` — matching this session's own
earlier live-confirmed finding that Note-Off velocity is always `0x40`)
for a separate voice slot going quiet. This is a real note on/off engine,
not button/state bookkeeping — a different subsystem from everything
mapped in part 1.

**Each voice's actual pitch comes from a clean, fully-decompiled utility,
`FUN_08018ee0_noteval`**:

```c
uint FUN_08018ee0_noteval(int voice_value, int base_offset, uint transpose)
{
  int note = voice_value + base_offset - transpose;
  // clamp into [0, 127] by adding/subtracting octaves (12 semitones) until it fits:
  while (note < 0)   { voice_value += 12; note = voice_value + base_offset - transpose; }
  while (note > 127) { voice_value -= 12; note = voice_value + base_offset - transpose; }
  return (uint8_t)((voice_value + base_offset) - (transpose & 0xff));
}
```

Called as `FUN_08018ee0(voice_slot_reg, *(sbyte*)some_global, *(sbyte*)(fp+0x4f))`
— i.e. **the per-voice output pitch is `voice_slot_value + a shared global
byte - a per-instance struct field (`+0x4f`, right next to the confirmed
flag/velocity pair at `+0x4d`/`+0x4e`), octave-wrapped into MIDI range**.
This is a genuine, general-purpose transpose/voicing arithmetic utility —
clean, simple, and exactly the shape needed to derive several
simultaneous output notes from one input event and a small set of
per-voice parameters.

**Honest assessment of confidence — this is strong circumstantial
evidence, not proof of the exact chord mechanism**:
- **Solid, directly observed**: the `+0x4d` flag (the same one the Chord
  button toggles) gates whether a given voice slot fires a note at all;
  the resulting Note-On/Note-Off messages are byte-for-byte correct MIDI;
  the pitch arithmetic is real, clean, and voice-indexed.
- **Not yet confirmed**: that this specific loop is *the* chord-expansion
  code rather than the *general* polyphonic voice-allocation engine used
  for every note the instrument ever plays (held keys, arp output, and
  chord expansion might all funnel through this same generic multi-voice
  dispatcher, with chord mode simply being "more voice slots get their
  flag set per key event" rather than distinct code). Given this
  session's confirmed live chord shapes were fixed musical intervals
  (root+3+7 for a minor triad, root+12+24 for an octave stack, not a
  simple per-voice-index-as-semitone-offset pattern), **the interval
  table or logic that decides *what* to put in the shared "global byte"
  parameter per voice — the actual musical shape (minor 3rd, fifth,
  octave, etc.) — has not been found yet**. This function computes the
  final pitch given an interval, but not where the interval itself comes
  from for each voice.
- **Concrete next step, not yet done**: trace backward from the global
  byte parameter passed into `FUN_08018ee0` for each voice slot — that's
  where a per-voice interval (or a lookup keyed by the Type/Notes knobs'
  confirmed CC 98/99 values) would be read, and would be the closest
  thing to "the chord interval table" this project has been looking for
  all session.

### Genuine dead end on the exact interval-source literal — moving on, not forcing it

Attempted the concrete next step above (trace the "global byte" operand
back to its source for each voice-slot call site). Hit a real, confirmed
contradiction rather than a soft "couldn't find it": the `ldr r3, [pc,
#0x294]` instruction at `0x080185ba` (loading the pointer later
dereferenced by `ldrsb.w r1, [r3]`) was verified bit-by-bit —
`0100101110100101` decodes unambiguously as T1 `LDR (literal)`, `Rt=3`,
`imm8=165` (scaled `0x294`), giving a **provably correct** literal-pool
address of `0x08018850`. But the actual bytes stored there
(`fa f7 c4 f9 ...`) decode to `0xf9c4f7fa` as a 32-bit word — not a
plausible pointer in flash (`0x08xxxxxx`) or RAM (`0x20xxxxxx`) range by
a wide margin, which would fault if the CPU genuinely tried to
dereference it. Checked three independent ways (manual bit-level
instruction decode, direct raw-byte read at the pool address, and a
forced Ghidra disassembly of the surrounding region) — all agree on the
same numbers, none resolve the contradiction. Most likely explanation:
this specific literal pool sits somewhere other than where a
straightforward reading of the encoding suggests (an inline-literal/code
interleaving issue at a finer grain than anything resolved elsewhere this
session), but the exact reason isn't pinned down. **Logged as a genuine
local dead end and set aside rather than force an unsupported
conclusion** — per this project's standing rule, a contradiction that
can't be resolved is reported as exactly that, not papered over. Revisit
only with a different technique (e.g. real emulation of this specific
instruction sequence) if this thread is picked up again.

took a materially different approach — instead of hooking the native
arp/sequencer engine's own step logic (our approach), it built a fully
independent mode entered via a dedicated gesture, interacting with the
native firmware only through an explicit, carefully-bounded adapter
contract. Given last night's result and their own "builder and consumer
together" caveat, the native engine's internal state (retention,
double-buffering, look-ahead release) looks more interconnected than a
single-hook patch can safely account for. Not adopting that strategy yet,
but recording it as a live, credible alternative for the next patch-design
decision rather than defaulting silently to more hook-patching.

## Root cause of the E0 hear-test failures, confirmed (not just externally-sourced) — 2026-09-22

Independently re-verified the external repo's retention claim by
disassembling `play_time_step` (`0x08013e8c`) and `seq_step_release`
(`0x0801415c`) directly, and traced both far enough to find the actual
note-emission gate. **The real answer, confirmed:**

`play_time_step` reads voice 0's **pitch byte** (via `seq_step_note`,
`0x080130e8`) near its very start and computes `(pitch + 0x7f) & 0xff`,
branching to an immediate function return if the result is `<= 1` —
verified by hand this is true for exactly `pitch == 0x81` and
`pitch == 0x82` and no other value. **This is the actual "does this step
attempt a note at all" gate**, and our patch never touched it.

Separately, `seq_step_gate` (`0x080130f4`, the function our patch
redirects) is consumed in exactly the way the external source described:
`seq_step_release` scans voices for pitch `== 0x81` first (tie), and
*only if none found* falls back to testing bit `0x80` of the gate byte
to decide whether to release a previously-held note. Inside
`play_time_step` itself, the same bit ends up in a local flag (`sb`) that
controls whether a *cached previous output pitch* gets written into a
retention-tracking array — bookkeeping for note-off/tie handling, not
whether voice 0's note starts.

**Conclusion**: last night's patch modified a real, meaningful bit — just
not the one that gates note emission. Clearing bit 7 would only ever
have affected tie/retention accounting, which is exactly consistent with
every hear-test showing a Note-On on every step regardless. This is now
a confirmed root cause, not a hypothesis.

**Concrete new hook candidate, not yet designed as a patch**: the real
gate is the pitch-byte check at `0x08013ebc`-`0x08013ecc` inside
`play_time_step`. A Euclidean/rhythmic patch could plausibly redirect
this specific comparison (or the branch it feeds) to also treat a
Euclidean "miss" as if pitch were `0x82` (the existing "no new note, but
not an unconditional Note-Off" sentinel — preserves tie/release
semantics correctly rather than inventing a new state), forcing the same
early-return path already used for that case. This is a materially
different, and likely simpler, patch design than `euclid_wrap`'s
gate-byte approach — not yet built or tested, and the strategy question
in the section above (native hook vs. independent mode) is still open
regardless of which specific hook point gets used.

## Revised patch designed and Unicorn-emulated (not flashed) — 2026-09-22

Built the pitch-byte hook proposed above: `pitch_gate_wrap`, a new
feature-gated block in `ks37_patch.S` (`FEAT_PITCH_GATE`, not wired into
any existing build level), replacing the single `seq_step_note` call at
`0x08013ec2` (voice 0's master-gate read inside `play_time_step`, not the
three `seq_step_gate` sites `euclid_wrap` uses). It calls the original
function unchanged, and — only when the returned pitch is *not* already
a native tie (`0x81`) or rest (`0x82`) — runs the same `euclid_gate(step,
8, 3)` check E0 uses, substituting `0x82` on a miss.

Assembled cleanly (132 of 1024 bytes used). Unicorn-tested directly
(hook redirected in an in-memory flash copy, no `.led` file built): 8
synthetic steps covering every combination — real-note hit, real-note
miss, pre-existing native rest on both a hit-numbered and miss-numbered

behavior exactly**: hits and pre-existing 0x81/0x82 pass through
unchanged; real-note misses become `0x82`.

**What this does and doesn't establish**: this confirms the wrapper's
own logic is correct, and — since the downstream `(pitch+0x7f)&0xff<=1`
check in `play_time_step` is unmodified and was already independently
confirmed to early-return for exactly these two values — gives strong
reason to expect this actually suppresses note emission on a miss,
unlike the `seq_step_gate` approach which provably couldn't. It does
**not** yet confirm this on real hardware, and does not account for
anything about the double-buffered current/pending sequence-block
mechanism or the release/look-ahead function noted earlier as
unexplored. **Not built into a `.led` image, not flashed, per agreed
scope** — this was a design-and-emulate pass only. Next step, if this is
picked up again: decide the native-hook-vs-independent-mode strategy
question first, then (if staying with the hook approach) wire this into
`build_patch.py` as a new level and test on real hardware.

## Root cause of the slot-dependence, confirmed by direct disassembly — 2026-09-22

Traced where `play_time_step`'s `step` argument (the value our hook
passes straight into `euclid_gate(step, 8, 3)`) actually comes from.
**It is not computed inside `play_time_step` and is not a counter our
patch controls.** At entry (`0x08013e8c`), `play_time_step` immediately
spills its own incoming `r1` argument to the stack (`0x08013e94`) and
reloads it at the `seq_step_note` call site (`0x08013ec2`) — the step
value is handed in by the caller.

`play_time_step` has exactly two callers, both of which write the same
value into **the same object field, offset `+0x38`**, of the active
sequence block:

- Caller at `0x08011ff0`–`0x08012028`: a dispatch function taking a mode
  flag in `r1`. On the `r1==0` path it reads the current step counter
  (`+0x38`), range-checks it against a **length field at offset `+0x10`**
  (`if step >= length-1: wrap`), increments and stores it back, then
  calls `seq_step_release` (tie/lookahead bookkeeping) — but does **not**
  call `play_time_step` on this path. On the `r1!=0` path it reloads
  `+0x38` (clamped non-negative, not incremented) and calls
  `play_time_step` with that value.
- Caller at `0x08012e56`–`0x08012ec0`: a different context computes a new
  step value via its own logic (compared against the previous value and
  against a signed byte at offset `+0x55`, suggesting a possible
  fixed/held-step override), stores it to the same `+0x38` field, and
  calls `play_time_step` with it.

**Conclusion**: the "step" our hook gates on is the native engine's real,
persistent step-position field for whatever sequence block is currently
active on the device — the same block the external repo's double-
buffered current/pending pointers (`0x20002c4c`) describe — bounded by
that block's own length field (`+0x10`), not an independent 0–7
Euclidean domain our patch invented. This is a direct, mechanical
explanation for the slot-dependent results above: a slot whose length
field happens to keep the counter permanently at (or oscillating within
values that are) always a Euclidean "hit" position under our fixed
`length=8,hits=3` math will show "every real step fires" regardless of
whether the patch is running correctly; a different slot's length
produces a different, but still fixed, subset of hit positions. **The
wrapper's own logic (confirmed correct in emulation) is not in question
here** — the input domain it's being fed is not what the design assumed.

**Concrete next step, not yet built or tested**: stop reusing the native
`step` value as the Euclidean gate's input. Maintain our own free-
running counter in patch RAM (a spare byte, e.g. reusing the
`FLAG_RAM`-adjacent scratch region already claimed by this patch page),
incremented once per `pitch_gate_wrap` call that sees a real (non-tie/
rest) pitch, and feed *that* counter into `euclid_gate` instead of the
native `step` argument. This makes the produced rhythm self-contained
and independent of whichever sequence slot/length happens to be active —
directly addressing the confirmed cause above without requiring a
strategy decision on native-hook-vs-independent-mode first (though that
question remains open regardless, see the Strategy note in
`docs/HANDOFF.md`).

## Fix built: own free-running counter (`STEP_CTR_RAM`), emulated, flashed image rebuilt — 2026-09-22

`step` argument at all (it's still passed through unchanged to the
wrapped `seq_step_note` call, since that's needed to fetch the right
voice-0 pitch for that native position — only the *Euclidean gate's own
input* changes). Added `STEP_CTR_RAM` (`0x20005F02`, next free byte after

## Density contradiction resolved: scorer bug, not live jitter — 2026-09-22 (verification)

Asked to re-derive why `pitch_gate_wrap` + `STEP_CTR_RAM` produced `1,2,2`
on some captures and ~90% every-step on others, same flashed e0b image,
single held key, no re-flash. Three results, all from the stock flash
extract plus the existing listen dumps (no new patch, no flash).

### Writer `0x080130cc` never emits 0x81/0x82

Leaf store: `strb r2` pitch, `strb r3` velocity into
`slot[(voice+step*8)*2]`. No compare, no rest/tie branch. Pattern's
generator loop at `0x0801196c` calls it with a table-driven pitch from
`0x08013de8` (clamped `>0x7f`). The only `0x82` writers found are
empty-input (`0x080137c4`), slot init (`0x0801163c`), and unused-step
fill (`0x080137f0` / `0x08013890`). One held key takes
`rebuild_order`'s `hold-count==1` path (`0x08011a60`): one real pitch,
then `bl 0x0801196c` only if `engine+0x10==6`. Native Pattern rests are
not compounding with the gate on the path that was tested.

### CC21 = internal + 1 (mapping closed)

Not a subtract on `set_arp_mode`. The CC *output* path at `0x08005a72`
does `adds r1, r0, #1; movs r0, #0x15; bl 0x08006914` after
`mode_byte_get` (`ldrb [r0,#0x55]`). Test-20 already showed CC21 = 1..8
= printed detent. Therefore `settings+0x55` / `engine+0x10` are 0..7
for those eight detents (`+0x55==8` is a separate no-CC state). Panel
Pattern (CC21=7) is TBH case 6. Panel Walk (CC21=6) is TBH case 5
(Order builder + play-time `0x08011878`). Last night's silkscreen
"Pattern" tests did hit the semi-random builder.

### Tick rate is not 2× on Arp

`play_time_step` has exactly two `bl` sites: `0x08012028` and
`0x08012ec0`. The first is `0x08011ff0` with `r1!=0`, and that function
is called from `0x080183c6` only when `*(0x20001124)+0x10==2` — a
different object from the arp engine at `0x20001094`. Arp uses
`0x08012ec0` inside `arp_seq_tick`, on step change (with a same-step
retrigger side path under flags). That is not a systematic double-fire
per audible step, and it cannot turn 3-in-8 into 90% hits.

### The dumps were 3-in-8 the whole time

No F8 clocks in any `e0-20260922-*.txt`. `_ioi_steps` used the shortest
IOI (~310 ms = 2T) as one step. Wall times on the "bad" 90% file
`e0-20260922-151333.txt` are `314, 465, 469, 316, 464, 470, …` — 2T and
3T. `round(3T/2T) = round(1.49) = 1` in Python, so the scorer printed
every-step. At T≈155 ms that file is `2,3,3` repeating, 100% 3-in-8.
Same for `141812`, `142418` (logged as every-step), `150355`, `155849`.

every-step has no 1.5× band, so `141445` still FAILs.

**Not a new patch.** The flashed counter-fix e0b already produces 3-in-8
on Arp/Pattern, one held key.
